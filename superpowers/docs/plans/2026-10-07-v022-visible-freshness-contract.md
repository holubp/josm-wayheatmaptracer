## User-visible contract

One visible attempt uses the actual selected imagery layer rendered over the selected segment at its fixed slide-time bounds, scale, zoom and chunk layout. Its candidate geometry remains in slide-time coordinates when the user pans or zooms. Confirmation, first Apply and each host Redo accept only the **same still-current source and exact immutable reviewed plan**. A change to a contributing tile, rendered pixel, layer owner, source definition, filter/processor, display offset/opacity, projection or effective attempt settings invalidates the attempt, even if a second raster happens to have equal pixels. Preview can remain inspectable, but Apply cannot silently fall back to cached evidence. Undo restores the prior dataset; a failed Redo changes no primitives and reports a fixed redacted reason. It may consume the attempted JOSM Redo entry, requiring a fresh alignment.

The contract covers Precise Shape and Move Existing Nodes, single selections and composed safe intervals with fixed manual-junction islands. Every interval and the composed plan share one capture owner/frame/source receipt; a fixed interval does not bypass source freshness. Review confirmation is session-local and becomes invalid when the source or chosen plan changes. No network, render, cache read, tile wait, or other blocking acquisition runs inside `DataSet.update`.

## Supported-source decision

* **Direct managed tiles** retain their existing `ManagedSourceReceipt`/coordinator-generation contract and are outside this visible-render design.
* **Plugin-owned `ManagedHeatmapLayer` rendered as a visible source** is the first candidate with identified controllable extension points in JOSM 19555; ordinary external classes remain unproved. Its protected initialization/cache/loader hooks and virtual tile factory permit investigation of a complete writer protocol. Its existing epoch and completion callback do not already provide that protocol. It is **not supported for Apply today**: `AlignWayAction.requireSupportedApplySource` rejects first Apply because JOSM image processors bypass the current epoch. Enable it only after the provenance and host tests below pass.
* **Arbitrary external `ImageryLayer`**, including ordinary TMS/WMS and third-party subclasses, has no proved complete render-change epoch or atomic snapshot lease in the available JOSM API. `TileCache` exposes get/add/clear/count/size but no revision; `Tile` exposes mutable image/load state; `ImageryLayer.getImageProcessors()` returns its mutable live list, and `addImageProcessor`/`removeImageProcessor` do not notify the tile layer. A repeat render can prove its sampled pixels at that instant, but cannot protect host Redo against later tile/cache/filter changes between that render and the dataset transaction. Do not treat its raster hash, layer instance/name, or selected tile URL as a current-source receipt. Fail **before expensive acquisition** with a clear supported-source explanation for an Apply-capable action, while retaining any explicitly read-only diagnostic preview route. This remains an **original-scope stable-release blocker** unless the maintainer explicitly changes scope or a later design proves an external-layer adapter.

No new global preference, implicit source switch, or managed credential validation for rendered imagery is proposed. The plugin-owned rendered layer must still reject if its own provenance cannot be established for this capture; it cannot silently use direct managed evidence instead.

The external-layer statement is an open capability proof, not a universal
impossibility claim. Normal `TMSCachedTileLoaderJob.loadingFinished` publishes
image/load state through unsynchronized Tile methods before notifying the
layer. An observer-only layer callback or Tile monitor therefore has a real
publication gap even after repeat capture. A concrete external adapter could
still succeed with complete decision dependencies and an actual shared writer
protocol. Arbitrary hidden third-party processor state is a separate unsupported
capability, not evidence that every ordinary JOSM TMS/WMS adapter is impossible.

## Minimal immutable receipt and lifecycle

`VisibleCaptureReceipt` should be produced with `VisibleRaster` and bound to the exact `ManagedHeatmapLayer` instance and an immutable plugin-owned watch. It records, privately, owner identity, complete tile-dependency addresses and per-address publication revisions (including any JOSM fallback/overzoom contributors), render-settings revision/fingerprint, source-definition identity, projection, frozen capture bounds/scale/zoom/chunks, and final raster evidence hash. Any secret-derived source-definition fingerprint is internal only: never export it through sourceIdentity, owner hash, lineage, logs or exceptions. Public diagnostics use a session-local opaque owner token and allowlisted nonsecret fields, safe numeric generation/revision, tile counts, zoom and source-status reason. The receipt is not valid unless the layer proves every contributing image or blank/placeholder decision was observed and no relevant load or mutation remained pending through the complete capture.

Declare the mutation model before implementing the receipt: ordinary source/UI
mutations are confined to an uninterrupted EDT operation; asynchronous tile
publication uses a governed writer protocol; unknown mutable processors fail
capability unless they expose immutable/versioned snapshots. Post-mutation UI
callbacks are useful only with that EDT confinement argument. They are not a
background publication barrier. Govern the actual processor backing list and
its normal mutation paths; account for constructor-time virtual add calls.

Separate **source mutation** from **view motion**. Panning/zooming the ordinary map is not a source-settings change and must leave the captured source receipt valid when it touches no contributing tile. An unrelated tile completing elsewhere must not invalidate merely because a global layer revision advanced. A contributing tile publication, replacement, cache clear, changed render filter/processor, offset/opacity, layer removal/replacement or source-definition mutation invalidates. If JOSM cannot reveal the actual fallback contributors for a frame, fail that capture rather than guess from the nominal zoom or a geographic tile rectangle. A pending relevant tile load makes the frame nonstable; at most a bounded, cancelable retry may occur **outside** the command transaction.

The plugin-owned layer's watch must encompass its governed tile publication, loader submit/completion/failure/cancellation, cache clear and error-clear, display/filter mutations under the declared execution model, visibility/name/opacity/destroy, and all supported processor addition/removal or direct-list mutation paths. A load-start or failed refresh makes a dependency temporarily unavailable as specified by its lifecycle; do not silently define every attempted load as a historical content change. Observed actual source publication invalidates even if pixels match. Guard or reject mutable processors that cannot supply a stable snapshot; verify built-in values and inventory as a second check. `ImageryInfo` needs controlled ownership or a proved normal-host EDT mutation path; a fingerprint alone does not establish mutation history. The watched layer must remain the resolver-selected, visible, live layer in the active LayerManager. Missing a normal supported mutation path prevents certification.

The dependency collector must be capture-scoped and thread-safe: JOSM tile
visitation uses parallel streams. Record actual lookup/miss and fallback/blank
decisions across all chunks, not only drawn images or a ThreadLocal set. Include
ReprojectionTile publication and decisions or record that exact unsupported
class/projection gap. Per-address revisions survive object replacement; bound
receipt retention and distinguish cache eviction from content publication so
unrelated map motion/loading does not invalidate the captured source.

Capture starts on the EDT after immutable effective settings and source owner are resolved. Begin the owner watch before virtual-viewport capture, record each chunk's actual used tile contributors and zoom, and finish the receipt after viewport restoration and a stable watch check. A virtual viewport transition must not itself count as changed source. Candidate selection/confirmation and first Apply repeat the same frozen frame outside the dataset lock and compare full raster/frame evidence, owner and watch receipt. Host Redo performs the same bounded preflight outside the lock. The current-source check rejects a changed watch even if the rerendered pixels match. The immutable plan and network/referrer receipt are revalidated at Apply/Redo as they are today.

Immediately before DataSet.update, acquire a short in-memory publication lease and recheck the prepared receipt. Inside the update, perform only bounded in-memory receipt/network checks and immutable plan application, then verify before releasing the lease. Prepare/decode pixels outside that lease and the dataset lock. State one lock order for host tile/cache/layer monitors, publication lease and dataset lock. Do not take the lease from a getter called under a tile monitor while a publisher holds the lease awaiting that monitor; do not hold it across parallel painting or invokeAndWait. A post-check plus rollback is sound only under the actual writer protocol and linearization proof. Reentrant same-thread source changes require exact rollback. A global epoch is insufficient because unrelated loads must not invalidate the attempt.
